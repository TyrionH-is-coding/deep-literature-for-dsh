## 不变的公共与持久合同

### 数据库与版本

`library_schema.py:19` 固定 `TARGET_VERSION=4`。新库直接 v4；既有 user_version 0/1 视作 v1 验证迁移，v2/v3 依次补结构，经备份后升级到 v4，失败恢复备份，其他版本拒绝。v2 增 folders/batch_operations/library_meta 及 items 列；v3 增 review_sessions/review_conclusions 绑定外键；v4 增 evidence_json、basis（legacy 默认）。已是 v4 仍会补结构/搜索索引并验证，不是纯只读操作。`LibraryService.__init__` 还开启外键并安装 membership revision trigger。

### Pipeline 与作业恢复

- `ReadingPipeline.start(paper_id, provider_profile='none', *, expected_parent_job_id=None)`；`advance(parent_job_id, supplied_input=None)`；`inspect(parent_job_id)`。返回 `ReadingPipelineState`，合同 `reading-pipeline-v1`。`inspect` 也会修复失活 worker 状态并同步库指针，不能作为无副作用的文件读取。
- 阶段顺序固定：`ensure_pdf → parse_mineru → translate_full → render_reader → schedule_derived_updates`。`stage_runner(stage, state, supplied_input)` 是现有注入点；默认适配器当前在 `reading_pipeline.py:180`，没有在本卡抽离。
- 状态保留 paper_id/parent_job_id/current_stage/state、stage_jobs/outputs/timings、source_pdf_sha256/reader_source_sha256、required_action、last_error 和时间。缺 PDF、用户/agent gate、失败与已完成状态不等于可以无条件重试；`advance` 持有 job claim，source hash/父 job/库活动指针共同控制恢复。
- `jobs/job_*/request.json`、`status.json`（scope、PID、heartbeat、required_input）、`events.jsonl`、`worker.log`、`resume.json`、`reading_pipeline.json`；workspace `papers/<paper_id>/job.json` 与 `generations/<SHA前16位>/job.json`；SQLite active_job_id、活动产物指针及来源 SHA 应一起核对。不能仅凭旧 PID 或一个 JSON 状态宣布恢复成功。
- job ID 由 BackgroundRequest 的规范化 JSON SHA256 前16位构成 `job_<hex>`；request identity 包括 paper、stage、input_hash、payload。`background_store` 的状态迁移、claim、launch claim、PID 生存检测是独立持久边界，本项不改变。

### 产物与旧格式

`full_read_models.py` 保持 `full-translation-v3`、审核 `full-review-v2` 与替换式 `full-review-v3` 的现有读取/校验。`mineru_models.py` 保持 `mineru-normalization-v4`；旧规范化恢复由 `normalization_upgrade.py` 和既有测试约束。`package_manifest.py` 保持 `generation-package-manifest-v1`、version 1，条目有 kind/path/contract/version/sha256，覆盖 source PDF、parser/reader/export manifest。manifest 只在 generation workspace 生成；旧 base workspace 与历史产物兼容路径仍由 `_resolve_artifact` 实现及 artifact_resolution、Reader 与 normalization 测试约束。本卡没有制造新版本或宣称任意历史格式均可读取。

### TypeScript 宿主与 scope

`src/cli.ts:384` 的 `engineJson(config,args,input?,env?)` 通过 UTF-8 stdin 发送 JSON，返回 `{ok,exitCode,stdout,stderr,json}`；runEngine 使用 `--data-root`，把 CLI 0/2/3 视为协议有效结果（成功/user gate/agent gate），不能把 `ok` 简化成流水线已经完成。

`engineStartFullRead(config,paperId)` → `full-read-pipeline-start`；`engineContinueFullRead(config,jobId,suppliedInput)` → `full-read-pipeline-resume --input -`；`engineAttachAndResumeFullReadPdf(config,paperId,jobId,pdfPath)` → `full-read-pdf-attach-resume`，均返回 `{ok,json,stderr}`。可信 provider 环境由宿主封装，不从模型参数接收任意环境。

`withEngineScope<T>(scope,action):T` 在 AsyncLocalStorage 中传递只读 scope，`SR_SCOPE_CONTEXT` 带 instanceId/scopeSessionId/scopeFolderId，可选 scopePaperId/scopePaperRevision。Python `use_scope` 严格检查字段，`capture_scope` 将 scope 与 paper revision 固定到 job 状态；发布时查询当前 SQLite 的分类/归档/revision，拒绝过期 scope。scope 不属于可让模型随意填写的工具参数。工作台从已安装包加载 `lib/cli.js`、`lib/engine_scope.js` 的桥接依赖不应因未来内部拆分消失；package exports 仍为当前 root/client/patch/package.json。

### F2：库恢复不等于整实例恢复

`scientific-reading-backup-v1` 库备份包括 SQLite、generations 与未完成 jobs，排除 secrets、runtime、downloads、status、临时/锁、launch.json 等。restore 只接受空目标、验证路径与 hash、迁移到 schema 4、重绑定执行路径；running/queued 作业转 interrupted，流水线必要时回 queued，下载/批作业要求重新提交，返回 `automatic_resume=False`。宿主原生 session/handoff、实例身份绑定不是该引擎库备份独立承诺的恢复域。已有 library_backup 测试覆盖关系/资产/未完成作业与失败原子性；未覆盖完整宿主实例恢复。F2 后续应由总控的独立恢复任务处理。

## 优先交接：F1 冲突合同与最小修复边界

实测 [f1-reproduction.json](evidence/f1-reproduction.json) 与 [可重放诊断](../../scripts/v02-audit-f1.py)：在临时库写旧值→导出 Excel→直接 SQL 写新值→refresh，三项 `personal_thoughts`、`understanding_level`、`user_notes` 全回到旧值，仍返回 success。这是精确的存储冲突，不冒称所有 UI 编辑入口均复现。

根因位置：`xlsx_snapshot.py:53` refresh 首先 import_user_fields；`:464` 之后只核验 `_身份`、列名、重复/未知 paper_id，`:547` 附近对三个字段执行无版本条件的 UPDATE。已有码的 `xlsx_conflicts` 是身份冲突，不是内容新旧冲突。库 membership revision 是分类/scope revision，不可直接冒充个人字段内容版本。

建议下一张单目标卡只定义并修复“旧快照与新 SQLite 个人字段冲突”，先由总控确定权威来源与冲突返回合同。建议合同：没有 Excel 改动时不回滚较新的 DB；只有 Excel 改动且 DB 自快照未变时可导入；双方不同改动保留双方证据并显式报告冲突；清空是显式编辑，不能被当作缺值。旧 workbook 没有基线信息时须有保守处理策略，不靠文件 mtime 推断哪条记录更新。

最小变更应聚焦 XlsxSnapshotService 的快照基线/三方比较或等价条件写入、必要的调用方结果处理及回归；保持 schema 4、pipeline、background_store、翻译/审核格式和上述 TS 入口，不借机做存储重构。是否用 workbook 隐藏表或现有 library_meta 保存基线需在下一卡明确；本项仅建议，未实施或裁定产品取舍。
