# 按模块开发

本仓库以 `v0.1.0-rc.6` 为恢复基线。当前项目状态入口是 `PROJECT.md`；开发任务以 `docs/project/tasks.json` 和对应任务卡为准。当前架构入口是 `docs/modules/README.md`，模块登记以 `src/modules/catalog.json` 为准。产品版本与模块版本分开；模块化开发不等于新版本已发布。

## 开始任务

1. 检查 Git 状态，保留已有修改。先运行 `npm run modules -- list` 定位职责，再运行 `npm run modules -- context <模块名>`。
2. 读取该模块说明、公共入口、任务涉及的实现和测试。仅在接口或依赖确实相关时扩大阅读，不默认加载全仓库、全部历史计划或其他模块实现。
3. 写清任务编号、本轮目标、涉及模块、基线提交和验收条件。遵守 `docs/project/session-protocol.md` 和 `docs/project/auto-loop.md`：总控已获用户授权自动派发后继任务，最多两个经独立性检查的开发任务并行，合入串行。跨模块变更先说明接口影响，再按依赖分步完成。台账中的 planned 条目本身不是开发者自行开工的指令。

## 修改与验证

- 内部模块之间通过 `src/modules/<模块名>/index.mjs` 访问；内部实现不跨模块直接导入。旧 `src/*.mjs` 兼容入口保留，新增业务逻辑放在所属模块。
- `application` 负责组合与启动，`tooling` 负责开发和发布工具；`oauth/` 保持独立包。文献引擎是锁定的外部制品，本仓库没有其实现源码，参见 `docs/modules/engine.md`。
- 用 `npm run modules -- impact --base <本轮基线提交>` 检查影响，再用 `npm run modules -- test <模块名>` 执行模块及依赖它的模块测试。修改范围扩大时扩大验证；纯文档改动以链接、事实和差异检查为主。
- 涉及边界、登记或版本变化时运行 `npm run modules -- check`。发布前执行对应发布验收；不能用单测代替真实安装、登录或科学内容验收。
- 记录实际执行的命令、结果和未验证项；旧报告与拟执行检查不能写成当前通过结果。

## 交付与追溯

- 每个可独立解释的模块变更使用明确的提交范围，例如 `fix(workflow): ...`。在提交或变更记录中写明模块、接口变化、验证证据和回退条件。
- 模块版本用于追溯接口及实现；发布仍锁定完整代码、依赖与引擎组合。不要从不同发布中随意拼接模块文件，也不要把代码回退理解为文献库或凭据回退。
- `docs/superpowers/plans/` 和阶段验收文档保留为历史资料；其中的旧任务、授权措辞和待办不构成当前指令。恢复旧计划前核对实际代码与用户本轮目标。
- 项目上下文包不包含凭据、真实文献内容或用户安装目录。不要为模块化修改用户已安装的工作台。
