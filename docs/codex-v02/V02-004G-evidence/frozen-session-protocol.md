# 总控与任务 session 协作

总控 session 长期协调，开发 session 按任务创建，复核 session 仅在影响较大时独立建立。模块是上下文边界，session 不是模块的永久容器。

## 当前节奏

- 用户已授权自动推进后继任务及互不影响的任务并行。开发任务并发上限为 2；共享文件、接口或有序依赖相冲突时串行，集成始终串行。具体门槛见 [自动总控循环](auto-loop.md)。
- 新开发任务从总控指定的精确 commit 创建独立 worktree；有依赖的任务顺序进行。首个验收任务可以针对尚待验收的候选，但必须明确其状态；后继实现任务使用已验收基线。
- 本轮先建立台账和可直接投递的任务卡。卡片 ready 不代表 session 已创建或已经运行；任务 ID、真实 session ID 和分支分别登记。
- 总控根据本轮用户持续授权，通过应用任务接口创建新的开发任务，无需逐任务重复确认；临时审查子代理不冒充用户可见开发任务。授权范围仍是当前 v0.2 稳定重构路线。

## 总控职责

1. 维护 PROJECT.md、任务台账和决策；冻结目标与非目标。
2. 给任务指定精确基线、允许修改的文件/模块、接口、验收条件、恢复条件。
3. 保留开发输出，独立检查证据与代码；发现跨模块影响时调整任务卡和调用方验收。
4. 组织集成与最终使用验收，更新完成状态；由实际证据决定后继任务是否 ready。

## 开始任务

新 session 只读取 PROJECT.md、自己的任务卡、目标模块说明及公共接口、与本任务相关的代码/测试。历史方案只按任务卡点名阅读。

启动前检查 Git 状态、HEAD、目标 worktree 与指定基线是否一致。基线缺失或已有用户修改时保留现状并报告，不能自行 reset 到“看起来差不多”的提交。

总控先登记完整 `baseCommit`、`worktree`、`branch`、`dispatchState` 和允许写入的路径，再派发。真实 session ID 可用时填写 `ownerSession`；只有 clientThreadId 时保留 queued，不伪造运行确认。应用列表不可见但固定工作树的任务回执、执行证据已经证明开工时，可以记为 in_progress，并明确 session 关联缺口。queued/reserved 也占用并行名额，避免重复派发。任务卡和项目入口应随指定 contextCommit 可读取；开发者只处理当前任务，不自行领取下一项。

台账中 `kind: workstream` 是候选工作范围，`milestone` 是验收/发布门槛；均需总控拆出单目标任务卡后才能分派。基线结果不支持继续重构时可以标为 deferred，记录原因并更新下游依赖。开发卡使用[任务模板](task-template.md)。

## 结束交接

每次交回：任务 ID；仓库、基线与最终提交；改动模块；接口/数据格式变化；逐条验收结果和证据路径；未执行事项；已知问题；恢复点与数据兼容条件。

证据必须指向当前提交和相同制品。不同候选的测试结果不能拼成一个“全部通过”；生成了测试文件不等于运行过测试。

状态流为 `planned → ready → in_progress → review → integrated`。失败依赖标为 blocked 并附明确原因。review 表示待总控验收；只有合入指定集成基线并完成必要读回后才 integrated。一个任务可以交回“未通过”，不能为了结束对话隐瞒未完成项。

任务结束后更新仓库记录；下一任务开新 session，不复制完整旧聊天。留存可复用决策和当前事实，废弃假设留在对应历史记录里。

## 分支和资料

- 稳定 main 保持可恢复；总控计划保存在 `codex/v02-control`。
- 开发与复核不同时修改同一工作目录；跨仓库任务记录两套精确版本。任务卡和源码不在同一仓库时，分别固定 `contextCommit` 与代码 `baseCommit`，提供必要资料包，避免依赖另一个目录的可变文件。
- 代码可以按模块撤回，发布仍构建一套经过验证的组合。
- 真实凭据、文献库和运行实例不是默认开发资料；合成样例与脱敏证据优先。现有产品授权边界不由任务卡里的历史引用扩大。
