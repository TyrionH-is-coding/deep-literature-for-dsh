## 阶段、持久状态与副作用合同

入口是 `ReadingPipeline.start/advance/inspect` 与 worker/CLI 的 full-read-pipeline start/resume。`start` 本身不执行阶段。`advance` 一次执行一个阶段；worker 循环推进直到 gate/失败/完成。下表的 parent 是同一个稳定 background job，并非每阶段都有 background child。

| 阶段 | 输入 | 成功及持久输出 | gate / 失败与实际续接 | 副作用归属 |
| --- | --- | --- | --- | --- |
| ensure_pdf | canonical paper metadata、受信 provider profile、已有 PDF 或 provider | `source.pdf`，base `job.json` 的 pdf_acquisition；parent `source_pdf_sha256`、ensure 输出；下一阶段 queued | 无 PDF → `needs_user` / `pdf_required`；worker `waiting_user`、exit 2；attach-resume 或经校验的 resume 输入 | TrustedPdfAcquisitionService 验证/发布 PDF、库 PDF hash；换源使旧 Reader stale，不删除旧正式文件 |
| parse_mineru | 同一 source SHA、generation workspace、method auto、受控 provider | staging 验证后发布 `parsed/mineru/{raw,full.md,source_map.json,parse_report.json}`、asset/package manifest；generation completed stage，再采用到 base job 指针；parent 下一阶段 queued | provider 配置/API 错误可转 `waiting_agent`、exit 3；其他异常 parent failed、worker failed/4；必须显式 `{}` 续接。真实进程中断边界见 F1 | 默认适配器内直接调用 MineruParseService；没有独立 parse child。provider 可重试；提交前不承诺 exactly-once |

持久域必须分开核查：

1. `jobs/<parent>/request.json/status.json/events.jsonl/reading_pipeline.json`：request 规范化 identity SHA 前 16 位生成 job ID；status 是 worker 状态，reading_pipeline 是阶段状态，二者并非总是同一字符串。`resume.json` 是 launcher/CLI 交接输入。
2. `jobs/<xlsx child>/.../launch.json`：独立进程与状态。默认 pipeline 的 `stage_jobs` 可为空；xlsx ID 保存在 schedule stage output。
3. SQLite：schema 4；active_job_id、source hash 对 parent 身份与发布有效性有作用；artifacts 的 reader path/status 是正式可用性指针。换源后的旧 Reader 可以保留 path/bytes，但状态变 stale。
4. `papers/<id>/job.json` 采用 generation parse pointer；`generations/<SHA前16>/job.json` 记录实际阶段。正式文件、未提交 staging、库指针不能相互冒充。

## 重复输入、并发与恢复保证

- 六个独立场景中同一源重复 start 的 parent ID 一致；完成后重复 advance/start 不重跑 stage。新增 Reader 保护测试核对完成后 artifacts 的 path/status/updated_at 原样，Reader bytes/mtime 不变。
- 同一进程之外的 advance claim 在活跃 worker 持有 `.claim_reading_pipeline` 时被拒绝；全库 heavy claim 限制 parse/translate。三条 kill 场景均实测该竞争。不是“并发双 start 对所有时间窗口线性化”的证明；也没有测量 provider 网络侧幂等。
- batch 相同提交实际调用 FullReadService 两次，第二次不改 bytes/mtime；不同译文同 batch → `translation_batch_conflict`。真正跨进程成功场景每个 batch 仅保存一次。合法换源产生新 parent/generation 是合理重建。
- parent failed/gate 且 `supplied_input=None` 不自动继续；显式输入才推进。CLI 对 failed/interrupted 只接受空对象，gate 接受特定格式；CLI 的 0/2/3 仍是有效协议退出码，不能将 gate 视作完成。
- `inspect` 检测 running 状态记录的 PID 已死时转 interrupted→queued，并同步 library；它不是纯读。job/heavy claim 使用 PID 生存性回收，launch marker 还有 start identity；不能将所有锁都描述为具有防 PID 重用的完整身份合同。
- 原始产物发布、parent checkpoint 与 SQLite 之间存在多次提交。已确认 parse 后恢复会再次进入 parse service，但命中 validated cache（provider 不重调）；没有将 service 调用次数与外部生成次数混为一谈。
